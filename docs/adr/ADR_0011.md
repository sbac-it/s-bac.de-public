# ADR_0011 – Standardstruktur der Component Library

**Status:** Gültig  
**Version:** 1.0  
**Datum:** 2026-07-31  
**Autor:** Sascha Bachmeier

---

# Kontext

Mit dem Ausbau des s-bac.de Design Systems wächst die Anzahl der Dokumente innerhalb der Component Library kontinuierlich.

Bereits erstellte Komponenten wie `07_INPUTS.md`, `08_FORMS.md` und `09_NAVIGATION.md` zeigen, dass eine einheitliche Dokumentstruktur die Lesbarkeit verbessert, die Pflege vereinfacht und den Wiedererkennungswert der Dokumentation erhöht.

Ohne verbindliche Vorgaben besteht das Risiko, dass zukünftige Dokumente unterschiedliche Strukturen, Terminologien oder Detaillierungsgrade aufweisen.

---

# Problem

Komponentendokumente unterscheiden sich in ihrem fachlichen Umfang.

Ohne eine gemeinsame Struktur entstehen unter anderem folgende Nachteile:

- uneinheitlicher Dokumentaufbau,
- unterschiedliche Begrifflichkeiten,
- erschwerte Navigation innerhalb der Dokumentation,
- höherer Redaktionsaufwand,
- geringere Wiederverwendbarkeit.

Es wird daher eine verbindliche Dokumentstruktur benötigt.

---

# Entscheidung

Alle zukünftigen Dokumente der Component Library **SHALL** einer gemeinsamen Grundstruktur folgen.

Die Struktur dient als Standard für sämtliche Komponenten des Design Systems.

Kapitel dürfen ausschließlich entfallen, wenn sie für die jeweilige Komponente fachlich nicht sinnvoll sind.

Die Reihenfolge der vorhandenen Kapitel **SHALL NOT** verändert werden.

---

# Standardstruktur

Die folgende Struktur bildet den verbindlichen Standard für Komponentendokumente:

1. Einleitung
2. Zweck
3. Ziele
4. Geltungsbereich
5. Abgrenzung
6. Grundprinzipien
7. Anatomie
8. Komponenten / Varianten
9. Zustände
10. Interaktionen
11. Responsive Verhalten
12. Accessibility
13. Design Tokens
14. Beispiele
15. Nicht zulässig
16. Verweise
17. Zusammenfassung
18. Dokumenthistorie

---

# Gestaltungsprinzipien

Alle Komponentendokumente **SHALL**:

- den Vorgaben aus `DOCUMENTATION_STANDARD.md` folgen,
- RFC-2119 (`SHALL`, `SHOULD`, `MAY`) verwenden,
- konsistente Terminologie verwenden,
- konkrete Design- und Implementierungsregeln definieren,
- Foundation-Dokumente referenzieren, anstatt Inhalte zu duplizieren,
- Beispiele enthalten,
- mit einer Dokumenthistorie abgeschlossen werden.

---

# Ausnahmen

Nicht jede Komponente benötigt sämtliche Kapitel.

Beispiele:

- Buttons benötigen keine Breadcrumb-Navigation.
- Icons benötigen keine komplexen Zustandsmodelle.
- Badges benötigen keine Mobile-Varianten.

Nicht benötigte Kapitel **MAY** entfallen.

Die Reihenfolge der verbleibenden Kapitel bleibt unverändert.

---

# Konsequenzen

Die Einführung einer standardisierten Dokumentstruktur führt zu:

- höherer Konsistenz,
- besserer Lesbarkeit,
- geringerem Redaktionsaufwand,
- einfacherer Wartbarkeit,
- höherer Wiederverwendbarkeit,
- professioneller Außenwirkung der Dokumentation.

Neue Komponenten können dadurch deutlich effizienter erstellt werden.

---

# Betroffene Dokumente

Diese ADR gilt für sämtliche Dokumente der Component Library.

Hierzu gehören insbesondere:

- 07_INPUTS.md
- 08_FORMS.md
- 09_NAVIGATION.md
- alle zukünftigen Komponentendokumente.
